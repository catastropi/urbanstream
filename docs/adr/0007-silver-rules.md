# ADR-0007: Silver 규칙 — 워터마크, 0값/결측, 장기 돌발, 기상 긴 형태

- 상태: 채택 (2026-11-04). 열 설계와 구현은 이 ADR 이후 5-1~5-4 에서 한다.
- 근거 자료: 5-0 프로파일 `data/profile/bronze_profile_20261103T152959Z.json` (Mac, Java 17 컨테이너에서 실행, 2026-11-04 00:30 KST).
- 관련: ADR-0001(봉투·event_time·dedup), ADR-0005(Bronze), ADR-0006(5단계 사전 결정), `docs/DEFERRED.md`.

## 0. 이 근거의 한계 (먼저 읽을 것)

프로파일은 **약 3.5시간 + 12분** 분량이다(11-03 16:15~16:26, 18:00~20:12, 11-04 00:15~00:27 KST). 평일 출퇴근 정점·주말·비 오는 날·심야 버스는 **한 번도 보지 못했다**. 아래 값은 "이 표본에서 문제가 없었다"는 뜻이지 "꼬리가 없다"는 뜻이 아니다. 그래서 Silver 는 Bronze 에서 다시 만들 수 있게 두고(체크포인트만 새로 파면 됨), 각 결정에 되돌리는 방법을 적는다.

## 2. 결정

### 2-1. 워터마크 (D-01) — 제안값을 그대로 채택, "잠정" 표시

| 표 | 워터마크 기준 열 | 지연 | 근거 |
|---|---|---|---|
| 도로소통·버스위치·버스도착 | `event_time` | 10분 | 최대 늦음 206초(3.4분)의 약 3배. 호출 간격(90~120초)보다 충분히 큼 |
| 돌발 | `fetched_at` | 10분 | 워터마크 dedup 을 쓰지 않으므로 상태 정리용일 뿐 (ADR-0006 7-B) |
| 기상 | `event_time` | 3시간 | 발표 후 15~64분에 도착(`source_age_sec` p99 3,818초). 기준시각이 시간 단위라 여유를 크게 둠 |

- `dropDuplicatesWithinWatermark` 의 상태는 키 수천 개 수준이라 지연을 길게 잡아도 메모리 부담이 작다고 **추정**한다(미측정, D-07). 반대로 짧으면 오래 멈춘 차량의 같은 GPS 시각이 다시 통과할 수 있다. 그래서 짧게 줄이는 쪽이 위험하고, 길게 두는 쪽이 싸다.
- **쓰지 않는 열:** Bronze `ingested_at` 과 `silver_processed_at` 은 어떤 판단에도 쓰지 않는다 (3절 시계 문제).
- 되돌리기: Silver 는 Bronze 에서 재생성 가능. 값을 바꾸면 **새 체크포인트 폴더**로 다시 시작한다(기존 체크포인트에서 워터마크 지연을 바꾸는 것은 하지 않는다).
- 재확인 시점: 평일 퇴근 시간대를 포함한 24시간치가 쌓이면 `scripts/silver_profile.sh` 를 다시 돌려 `lateness_sec` p99·max 가 위 표의 1/3 안인지 본다.

### 2-2. 0값/결측 (D-02) — 보존하고 표시만, 대체값 금지

이 표본에서 0 또는 결측은 **하나도 관측되지 않았다**: `speed_zero=0`, `speed_null=0`, `travel_time_zero=0`, `arrive_in_sec_zero=0`(최솟값 1), `arrive_in_sec_null=0`, `RN1` 원문은 `"0"` 6건뿐. 따라서 데이터가 정해 준 정책은 없고, 아래는 **규칙**이다.

- 값은 그대로 두고 `dq_flags`(문자열 배열)에 이름만 추가한다: `speed_zero`, `speed_null`, `travel_time_zero`, `arrive_zero`, `arrive_null`, `value_unparsed`(기상 원문은 있는데 숫자 변환 결과가 NULL), `ingest_clock_skew`(Bronze `ingested_at` < `fetched_at`, 정보용).
- 0 을 NULL 로 바꾸거나 평균으로 채우지 않는다. 의미(정체인지 결측 코드인지)를 모르기 때문이다.
- 기상은 원문 문자열(`value_raw`)과 숫자(`value_num` = `try_cast`)를 **둘 다** 둔다. 비 오는 날 `RN1` 이 `"강수없음"`, `"1mm 미만"`, 범위 문자열 같은 비숫자로 올 수 있는데 지금은 0 건이라 **모른다**(D-41). 그때도 행이 버려지지 않고 `value_unparsed` 로 남는다.
- `arrive_code=2` (99건, 0.56%)의 뜻은 **모른다**(D-43). 원문 그대로 둔다.
- 버스도착 `speed`(0~199, p99 79)는 단위 미확인(D-57)이라 이상치로 표시하지도, 제외하지도 않는다.
- 되돌리기: 플래그는 열 추가라서 규칙을 바꾸면 Silver 재생성으로 끝난다.

### 2-3. 장기 돌발 (D-03) — `planned_duration_days` 를 저장하고 `is_long_term = 7일 초과`

- 분포: `planned_duration` ≤1일 92건, >30일 2건, **그 사이 0건**. 첫 관측 시 나이(`age_at_first_seen`)도 같은 분포. 이 표본으로는 1일~30일 사이 어떤 값이든 분류가 같아서, **데이터로는 7을 고를 근거가 없다.**
- 7일은 **판단**이다: 우리 분석 단위가 주간 패턴이라, 일주일을 넘기는 돌발은 "새로 생긴 사고"가 아니라 "기준선의 일부"로 취급하는 편이 Gold 에서 안전하다고 본다.
- 제외하지 않고 표시만 한다(ADR-0006 7). `planned_duration_days` 원값을 같이 저장하므로 Gold 에서 임계값을 바꿔 다시 계산할 수 있다.
- 임계값은 설정 파일 한 곳(`config/silver.yaml`)에서만 읽는다.
- 재확인: 며칠 쌓이면 프로파일의 구간(1~7일, 7~30일)이 비어 있지 않은지 본다.

### 2-4. 기상은 긴 형태(행 = 관측 항목 1개) — 확정

스트리밍 `pivot` 은 지원되지 않는다(샌드박스에서 AnalysisException 확인). 가로 변환은 Gold(배치)에서 한다.

## 3. 프로파일이 드러낸, 결정에 영향을 준 이상 징후

1. **`ingested_at - fetched_at` 이 음수**(최솟값 -1,906초, 도로소통·돌발·기상에서 같은 값). 수집 후 32분 전의 시각이 적히는 것은 불가능하므로 **Spark 컨테이너 시계가 호스트보다 느렸던 구간이 있다**는 뜻이다. 수집 정지는 아래 3번처럼 잠자기로 확인됐지만, **시계가 어긋난 원인이 잠자기인지는 미확인**이다(가설: 깨어난 뒤 Docker VM 시계가 늦게 맞춰짐, D-44). 11-04 00:39 에 호스트와 컨테이너 시계를 비교했을 때는 일치했다.
2. **`pipeline_delay` p95 약 9,000초(2.5시간)**: 모든 소스에서 최댓값이 9,350~9,360초로 거의 같다. 한 번의 정지 뒤 밀린 메시지를 한꺼번에 처리한 흔적과 일치한다. 이 때문에 지연 판단에는 Bronze `ingested_at` 이 아니라 `event_time`/`fetched_at` 만 쓴다(ADR-0006 의 선택이 맞았음).
3. **수집 공백이 두 번**이다 (D-09): 11-03 16:26~18:00 과 **20:12~00:15 KST 안팎**(시간대별 건수에서 21·22·23시가 모든 소스에서 비어 있음). 원인은 둘 다 Mac 덮개 닫힘 잠자기로 확인했다(`pmset -g log`: 16:22:58 Clamshell Sleep→17:59:55 Wake, 20:12:53 Clamshell Sleep→00:20:59 Wake). 버스가 00시대에 없는 것은 설계(04~24시만 수집)와 일치한다.
4. 컨테이너 테스트: `21 passed, 57 deselected` → 컨테이너 전체 **78개**로 기대값과 일치.

## 4. 이 ADR 이 하지 않은 것

- 표별 열 정의·구현·테스트(5-1~5-4)
- Delta 도입, Bronze 압축, `backfill_from_raw` (ADR-0006 에서 보류)
- 링크 목록 확대(D-40) — 도로소통이 링크 1개라서 Silver 도로소통 표는 지금 사실상 한 줄 시계열이다

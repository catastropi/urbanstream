# ADR-0004 — Step 3: Kafka 토픽, 메시지 형식, Collector 설계

- 상태: 확정 (Step 3, 2026-11-02). 단, 갱신 주기와 호출 한도가 '임시값'이다 (결정 7)
- 관련: `config/topics.yaml`, `config/sources.yaml`, `collector/`, `scripts/create_topics.py`

## 배경

Blueprint H절(토픽)과 F절(아키텍처) 원문이 없어서, Step 0~2 에서 확인한 사실과 요청서 원칙(재처리 가능, 외부 API 장애 전제, event-time 중심, lineage)을 근거로 설계했다. 이름만 제안이므로 Blueprint 가 첨부되면 `config/topics.yaml` 의 이름만 바꾸면 된다(코드는 토픽 이름을 하드코딩하지 않는다).

## 결정 1 — 토픽 7개

| 토픽 | 파티션 | 보관 | 메시지 키 | 내용 |
|---|---|---|---|---|
| `urban.traffic.speed.v1` | 3 | 72h | `link_id` | 도로 소통 |
| `urban.traffic.incident.v1` | 1 | 72h | `acc_id` | 돌발 |
| `urban.bus.position.v1` | 3 | 72h | `veh_id` | 버스 위치 |
| `urban.bus.arrival.v1` | 3 | 72h | `route_id\|station_id` | 버스 도착 예측 (슬롯별) |
| `urban.weather.observation.v1` | 1 | 72h | `nx\|ny` | 기상 실황 |
| `urban.dlq.v1` | 1 | 7d | 소스 이름 | 계약 위반 행, 해석 못 한 응답 |
| `platform.audit` | 1 | 7d | 소스 이름 | 호출 시도 1회당 1건 |

이유
- **소스당 토픽 1개, 스키마당 1개**: 계약(`*_v1`)과 토픽이 1:1 이라 Spark 가 토픽별로 고정 스키마를 읽는다. 이름 끝 `.v1` 은 스키마 호환이 깨질 때 `.v2` 를 새로 만들어 옮기기 위한 것이다.
- **키 = 같은 대상의 메시지가 같은 파티션**: 한 차량(한 링크)의 메시지 순서가 유지된다. 파티션 수(3/1)는 임시값이다 — 처리량을 측정한 뒤 정한다. 파티션을 늘리면 키 배치가 바뀌므로 `create_topics.py` 는 기존 토픽을 자동 변경하지 않고 경고만 한다.
- **보관 72시간**: 원본은 `data/raw` 에 따로 있으므로 Kafka 는 재처리 완충 용도다. audit/DLQ 는 조사용이라 7일.
- `platform.audit` 이름은 폴더 뼈대의 `collector/README.md`(Blueprint 기준)에 이미 있던 이름이다.

## 결정 2 — 메시지: JSON, 키 문자열, 타임스탬프 = event_time

- value 는 `Record.to_dict()` 그대로의 JSON(UTF-8): envelope 11개 필드 + `payload`. 스키마는 `tests/contract/snapshots/*.json` 으로 고정돼 있다.
- **Avro/Schema Registry 를 쓰지 않는다**: 스택에 Registry 가 없고(메모리·구성요소 추가), 스키마 변경 방지는 스냅샷 테스트가 이미 한다. Spark 는 스냅샷에서 만든 명시적 스키마로 읽는다. 데이터량이 커지거나 소비자가 늘면 재검토한다.
- **Kafka 메시지 timestamp 를 event_time 으로 둔다**: 소스가 시각을 주는 경우 처리 시각이 아니라 사건 시각이 브로커 타임스탬프가 된다 (원칙 'event-time 중심').
- 헤더: `schema_version`, `source_system`, `ingest_id`, `event_id` — 본문을 열지 않고 라우팅·추적할 수 있게.

## 결정 3 — 호출 실패는 전제하고, 종류별로 다르게 다룬다

| 종류 | 예 | 재시도 | 회로차단 |
|---|---|---|---|
| 일시적 | 네트워크 오류, 타임아웃, 5xx, 429, 깨진 응답, 처음 보는 코드 | 최대 3회, 1s·2s·4s(+지터), 모든 시도가 호출 예산을 쓴다 | 연속 5번 실패하면 300s 중단 후 시험 1회 |
| 영구적 | 인증 오류, 인자 오류, 게이트웨이 서비스 없음 | **하지 않는다** (같은 요청을 반복해도 소용없고, 인증 실패 반복은 키 정지 위험) | 즉시 열어 900s 쉰다 |

- 처음 보는 오류 코드는 계약에서 `unknown` 이다(추측하지 않음). 수집기는 이를 일시적으로 취급하되 시도 횟수가 제한돼 있다. 관측되면 분류를 추가한다.
- 회로차단은 대상(링크·노선) 단위다. 한 노선의 실패가 다른 소스를 멈추지 않는다.
- 해석 못 한 응답은 원본 위치(`raw_uri`)와 함께 DLQ 로 간다.

## 결정 4 — 호출 예산이 안전장치의 중심이다

한도를 모르는 API 가 있다(도로소통·돌발은 미확인, 버스는 '개발계정 일 1,000건' 가정). 그래서:
1. **시작 시 계획 검사**: (대상 수 × 활성 시간 ÷ interval)이 `daily_budget` 의 80% 를 넘으면 시작을 거부한다. 나머지 20% 는 재시도 몫이다.
2. **실행 중 소비**: 재시도를 포함한 모든 HTTP 호출이 예산을 쓰고, `data/collector/budget.json` 에 즉시 저장된다 → 프로세스를 재시작해도 하루 한도가 초기화되지 않는다. 날짜는 KST 기준.
3. 예산이 바닥나면 호출을 멈추고 audit 에 `budget_exhausted` 를 남긴다 (조용히 실패하지 않는다).

현재 계획 (모두 임시): 도로소통 60s → 1,440회/일 (상한 2,000, 근거 미확인) · 돌발 120s → 720 (상한 1,000, 미확인) · 버스 위치·도착 각 90s, 04~24시 → 800 (상한 1,000, 가정) · 기상 600s (같은 발표 시각이면 호출 생략 → 실제로는 시간당 1~2회).

## 결정 5 — 원본을 먼저 저장한다

모든 응답(오류 응답 포함)을 파싱하기 전에 `data/raw/<source>/<날짜>/<시각>_<ingest_id 앞 8자>.<확장자>.gz` 로 저장하고, 그 경로를 envelope 의 `raw_uri` 로 쓴다. 이유: 파서가 틀렸거나 스키마가 바뀌었을 때, 또는 Kafka 전달이 실패했을 때 원본에서 다시 처리할 수 있어야 한다 (원칙 '재처리 가능', 'lineage'). 용량: 버스도착 응답 12 KB(gzip) × 800회 ≈ 10 MB/일.

## 결정 6 — Kafka 전달 실패는 소스 장애가 아니다

발행이 실패하면(`delivery_errors`) 로그에 오류로 남기고 audit 에 기록하지만, 소스의 회로차단은 건드리지 않는다. 소스는 멀쩡하기 때문이다. 원본이 저장돼 있으므로 이후 재발행할 수 있다(재발행 도구는 Step 4 의 Raw 재처리와 함께).

## 결정 8 — 실행 방식

- **정정 1 (2026-11-03): 소스별 스레드.** 처음에는 단일 프로세스·순차 실행이었다(지연 최대 1.3초라는 관측 근거). 그 뒤 버스도착 호출이 26.2초 걸린 일이 있었고, 순차 실행에서는 그동안 다른 소스의 호출이 모두 밀린다. 그래서 `run` 은 **소스마다 작업 스레드 1개**로 돈다 (`run_forever_parallel`). 같은 소스의 호출은 겹치지 않고, 다음 호출 시각은 호출이 끝난 뒤(끝난 시각 + 간격) 정한다. 공유 상태는 보호했다: 호출 예산(잠금), Kafka 발행→flush→전달 실패 수 읽기(잠금, 다른 스레드의 실패가 섞이지 않게). **되돌리기:** `python -m collector run --sequential` 이 예전 방식이다.
- 시작 시 대상마다 3초씩 어긋나게 시작해 한꺼번에 호출하지 않는다. 간격에 ±5% 지터.
- 호스트(Mac)에서 `python -m collector run` 으로 실행해 `localhost:9092` 에 붙는다. 컨테이너화(Dockerfile)는 모든 구성요소가 준비된 뒤 Step 후반에 한다 — 지금은 코드를 고치며 바로 실행해 보는 편이 빠르고, 컨테이너 안에서는 주소가 `kafka:19092` 로 바뀐다(`KAFKA_BOOTSTRAP` 환경변수).
- `Ctrl+C`/SIGTERM 은 현재 사이클을 마치고 Kafka 버퍼를 flush 한 뒤 종료한다.
- 키는 `.env` 에서만 읽고, 로그·audit·DLQ·Kafka 메시지에 나타나지 않는다 (테스트로 확인: 실제 키 문자열을 가진 오류 메시지도 `***KEY***` 로 마스킹).

## 결정 9 — 호출 제한시간과 연결 (2026-11-03)

- `timeout_sec: {connect: 5, read: 10, total: 15}`. connect/read 는 '바이트 사이 간격'만 막아서, 조금씩 느리게 오는 응답은 총 시간이 길어질 수 있다(버스도착 26.2초 관측). 그래서 본문을 조각으로 읽으며 **총 제한시간 15초**를 확인하고, 넘으면 `timeout` 으로 분류해 재시도한다. 한계: 조각 사이에서 확인하므로 최악은 total + read(약 25초)다. 재시도한 호출도 호출 예산을 소비한다.
- 15초의 근거(관측): 정상 지연은 도로·버스 p95 0.3~2.7초, 돌발 p95 1.6초, 느린 사례는 4.4초와 26.2초. 정상 호출은 건드리지 않고 이상치만 끊는 값이다. read 를 20→10초로 줄인 것도 같은 근거다.
- `Connection: close`: 호출 간격이 60초 이상이라 연결 재사용의 이득이 없다. 60초 간격 측정에서 버스 서버만 `RemoteDisconnected` 가 40회 중 4번 났고 15~20초 간격에서는 55회 중 0번이었다(단측 p≈0.03, 표본이 작아 약한 증거, 원인은 확정 못 함). 매번 새 연결을 쓰면 '놀고 있는 연결을 서버가 닫는' 가능성이 사라진다.
- **되돌리기:** `sources.yaml` 의 `timeout_sec` 를 `{connect: 5, read: 20, total: 60}` 으로, `fetch.py` 의 `"Connection": "close"` 를 지운다.
- 확인할 것: 1시간 이상 연속 수집의 audit 에서 `attempts>=2` 비율과 `TotalTimeout` 건수.
